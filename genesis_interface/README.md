# Genesis Command Center V1.4

This interface is a local operator console over the existing Genesis Python runtime. The browser does not implement reliability reasoning.

## Run

From the `GenesisLabcl` project root:

```bash
python -m genesis_interface.server
```

Open `http://127.0.0.1:8765`.

## Workspaces

- Overview — latest engine result and session events.
- Fleet & Assets — asset information from processed observations.
- Telemetry — selectable observation history.
- Evidence Explorer — evidence summary and raw JSON result.
- Investigations — submit follow-up telemetry through the Genesis runtime.
- Reliability Memory — records currently held by the live engine's memory store.
- Incidents — records currently held by the live incident manager.
- Audit Trail — events generated by this interface session.

## API

- `GET /api/health`
- `GET /api/state`
- `GET /api/memory`
- `GET /api/incidents`
- `POST /api/reset`
- `POST /api/investigate`
- `POST /api/investigation/follow-up`
- `POST /api/scenario`

The follow-up endpoint submits a new telemetry observation. It does not assert that an engineer's claim is true and does not automatically validate a hypothesis. A future human-evidence workflow should use Genesis's dedicated human-evidence contracts and review lifecycle.

## Scope and safety

- The default R004 scenario uses synthetic telemetry, processed by the real Genesis engine.
- Memory and incident views show only records present in the current engine session. They do not claim persistence across restarts.
- This server binds to `127.0.0.1` by default. Do not expose it to a network without authentication, authorization, and appropriate deployment hardening.


## V0.7 telemetry observability

The Telemetry workspace renders motor temperature, battery level, and workload time-series from the observations returned by the active Genesis session. Missing measurements are omitted rather than interpolated. The quality panel reports the engine's observation-quality groups and security fields. Calibration validity and dedicated measurement validity are explicitly shown as `NOT EXPOSED` until the runtime supplies those assessments; this interface does not infer them.

Run from the project root with `python -m genesis_interface.server`, then open `http://127.0.0.1:8765`. The default scenario uses synthetic telemetry processed by the real Genesis engine.


### V0.8 — Interactive evidence-level trace
- Chart points can be selected by mouse or keyboard.
- Selecting a point identifies the exact recorded observation, displayed value, returned quality/security assessments, reliability state, assessment, recommendation, and structured evidence returned for that engine result.
- Source provenance, sensor identity, calibration, and raw transport data are explicitly marked unavailable when not exposed by the current runtime.
- The trace does not claim that every returned evidence item causally depends on the selected signal; it displays the evidence returned alongside that observation and preserves the boundary between telemetry and causal findings.


### V0.9 — Evidence lineage and theme controls
- Evidence Explorer lists structured findings and their engine-provided supporting data, source, availability, limitations, and any explicit upstream evidence IDs. It does not infer causal links when the engine does not provide references.
- A persistent light/dark theme toggle is available in the top bar. The selected theme is saved locally in the browser; if browser storage is unavailable, the control still works for the current page session.


### V1.0 — Engine-level evidence lineage
- Evidence synthesis now returns an `evidence_lineage` graph with stable evidence nodes, directed links, unresolved references, unlinked findings, counts, schema version, and explicit limitations.
- Engineering signals are linked to an observation only when the signal name identifies a known telemetry field and the signal value exactly matches that observation's value. The relationship is labelled `FIELD_VALUE_MATCH_NOT_CAUSATION`; this is a traceable association, not a causal claim.
- Contradiction links are built only from the contradiction record's explicit `supporting_evidence_ids`. Unresolved IDs are recorded instead of silently dropped.
- Evidence Explorer shows graph coverage counts and the relationship basis alongside each finding. The graph is partial when evidence has no explicit or conservative traceable link; that is intentional.
- Theme support remains available in light and dark modes.

Verification performed for this archive: `python -m pytest -q` — 590 passed, 11 additional subtests passed. JavaScript syntax and ZIP integrity checks were also run. These tests verify software contracts, not physical-world diagnostic validity.


### V1.1 — Temporal provenance checks
- Evidence nodes expose temporal scope only when it is present in the producing data. Single observations retain their numeric `time_step`; pattern evidence can expose its observed window; derived features explicitly state when their source window is not exposed.
- Lineage edges compare numeric time steps only when both ends provide comparable values. An upstream endpoint later than its dependent endpoint is surfaced as `TEMPORAL_ORDER_CONFLICT` for review.
- Evaluation time is kept distinct from measurement time. A signal's current evaluation step is not treated as proof of the sensor's acquisition timestamp.
- Unknown or incomparable clock/time semantics remain `TIME_ORDER_UNAVAILABLE`; timestamp strings are not coerced into numeric time steps.

### V1.4 — Pattern-window evidence lineage
- The lineage builder now creates explicit graph nodes for telemetry rows embedded in a pattern finding's `supporting_data.observations`. Each row links to the pattern using `OBSERVED_IN_PATTERN_WINDOW`; this records source-window membership, not causation.
- A current field-level observation connects to an embedded window row only when the field/value and numeric time step match exactly. Such links are labelled `FIELD_VALUE_MATCH_AT_TIME_STEP`, not causal support.
- Unlinked evidence is now counted by whether a node has any incoming or outgoing edge, rather than counting only evidence nodes that have incoming links. Counts separately expose total evidence items and added window-observation nodes.
- Evidence Explorer shows the actual graph relationships and their basis on each finding. Temporal conflicts on pattern-window links are surfaced for review.
- No window relationship is created when the pattern producer did not embed source observations; those findings remain unlinked.

Verification for V1.4: focused evidence/interface tests and full regression suite are run for the release. The default scenario remains synthetic telemetry processed by the real Genesis engine; this does not imply live sensor connectivity or prove causation.


### V1.5 — Derived-feature input provenance
- Derived temporal evidence now declares source rows using the same delta, lag, rolling-window, persistence, and acceleration selection rules as the feature contract. Current observation fields and historical input rows are linked to the derived feature with `INPUT_TO_DERIVED_FEATURE` edges.
- `thermal_rise` links to motor and ambient temperature only when the current values match the feature-contract formula.
- Historical input nodes include robot identity, row index, time step when available, and the input fields used. History is filtered to the current robot (plus records whose robot identity is absent) before lineage is built.
- Derived features expose their selected input window and selection method. Edges describe computational dependency, not causal proof. Features with missing history do not get fabricated input nodes or links.
- Verification: full test suite and JavaScript/Python build checks passed for V1.5. Tests establish implementation behavior only, not physical-world correctness.

### V1.7 decision provenance

The Audit Trail records a session-local decision envelope for each processed observation: input/result SHA-256 fingerprints, sequence, asset/time, returned state/transition, assessment, recommendation, and explicit runtime-versioning limitations. `GET /api/decision-records` returns these records. This is not a signed, durable, tamper-proof audit system, and hashes alone do not guarantee replayability.
